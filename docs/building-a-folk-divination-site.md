# 做一個民俗／占卜資料庫網站：folk.tw 的 43 天

> 這份文件把 [folk.tw](https://folk.tw)（台灣民俗信仰資料庫）從 0 到今天的經驗整理成
> **可以搬到別的傳統上的通則**。
>
> 如果你要做的是——印度的 Prashna／Kavadi 抽籤、日本的おみくじ、
> 歐美的塔羅與占星、易經卜卦、盧恩符文，或任何「有古老文本、有多種版本、
> 使用者帶著具體煩惱來查」的東西——本文對你有用。
>
> 如果你要做的是一般內容站或電商，跳過本文，這裡談的問題你不會遇到。
>
> 2026-08-02 整理。文中的數字都是實測，不是估計。

## 一、資料的誠實：這是唯一的護城河

占卜類網站在網路上**供給過剩**。籤詩全文、塔羅牌義、星座解析，
搜尋一下有幾百個站在寫，而且大部分寫得比你早、網域權重比你高。

你唯一能做而他們不做的，是**說清楚你的資料是哪來的**。

### 1.1 版本錨定：最重要的一件事

古老文本沒有「正確版本」，只有「哪個傳承的版本」。這件事在每個傳統裡都成立：

| 傳統 | 版本問題 |
|---|---|
| 台灣籤詩 | 同一支籤，各廟的籤版文字不同 |
| 塔羅 | Rider-Waite / Marseille / Thoth 的牌義與圖像系統不同 |
| 占星 | 回歸黃道 vs 恆星黃道，宮位制有十幾種 |
| 易經 | 通行本 / 帛書本 / 竹書，卦爻辭有異文 |
| おみくじ | 各神社自有籤本，吉凶等級數量都不一樣 |

我們的實測證據——同一句「福如東海壽如山」，接下去三句在三個廟版**完全不同**：

| 出處 | 第二句起 |
|---|---|
| 六十甲子籤第 36 首 | 君爾何須**嘆苦難**／命內自然逢大吉／祈保分明自平安 |
| 內門紫竹寺籤首 | 君爾何須嘆苦難／**榮華富貴天注定**／貴人太白守身邊 |
| 臺南大天后宮月老籤第 1 首 | 君你何須**問中間**／榮華富貴天注定／**太白貴人**守身邊 |

另一組，同一首的兩個廟版後半完全不同：

| 出處 | 四句 |
|---|---|
| 大天后宮月老籤 19 | 鬼**穿關門防**無常／鐵船過海**打**頭風／三畏鬼魂仇難解／運若去時惹禍災 |
| 內門紫竹寺 9 | 鬼**門關上遇**無常／鐵船過海**浪**頭風／口愿冤愆如羅網／爾欲嘉時得禍殃 |

**不指定版本，等於沒有內容。** 你寫「觀音靈籤第 30 首是這樣」，
使用者拿著手上那張籤來對，對不起來——那一刻你就失去他了。

#### 怎麼做

1. 每一套系統在資料層有獨立的 `id`、`count`、`sources`，不混在一起。
2. 每一首都有 `version_source` 欄位，寫明**依據哪個版本**，不是寫「網路整理」。
3. 來源分級，**只收得起的等級**：
   - ✅ 原始持有者官方公布（廟方官網、神社官網、出版社授權版）
   - ✅ 政府／學術典藏（有登錄號可引用）
   - ❌ 二手整理網站（全文找得到，但沒有版本標示——**收了等於前功盡棄**）
4. 同一首在不同版本有異文時，**不要合併、不要挑一個「比較通順的」**，
   分別當成不同系統收，或只收其中一個並寫明。

我們花了三輪、跨兩台主機的偵察去確認「觀音一百籤沒有可用的權威全文」，
**結論是不收**。三百多個網站有那一百首的全文，我們一首都沒放。

### 1.2 無源不發佈：留空比填滿好

站上有 76 位神明，其中 **7 位的 `sameAs`（維基資料連結）是空的**——
查不到權威條目就留空，不用「大概是這個」去填。

有一次要補灶神的造型描述，唯一的權威來源（政府網站）擋境外 IP 連不上，
**那個欄位就一直空著**，寧可空到今天。

這在機制上要做成 gate，不能靠自律：
- 資料有 `draft` 欄位，production build 時 `draft: true` 的實體**不對外顯示**
- 事實型實體（神明、活動）缺 `sources` 時，production 直接濾掉
- 完整性檢查會列出「待補狀態」清單，讓你知道有多少東西還沒源

### 1.3 一條很細但很重要的界線：挑選 vs 詮釋

我們的月老籤沒有自撰白話解，但籤版本身印著「婚姻好」「婚不可」這種分項判語。
在「感情」情境求籤時，我們顯示的是**籤版原文那三個字**，旁邊標「籤版原印」。

- **挑選**（可以做）：籤版有「婚姻」項，感情情境就取那一項給使用者看
- **詮釋**（不做）：把籤版的話改寫成我們的句子，然後不標示那是我們寫的

塔羅同理：牌義書寫什麼就標什麼來源；你自己的解讀要**明確分開呈現**，
不要混在一起讓使用者以為那是傳統說法。

### 1.4 資料本身會有錯，你要說出來

我們收了 330 首保生大帝藥籤（政府數位典藏），過程中發現原始典藏有錯：
- 第 71 首藥方有某味藥但說明沒解釋，第 72 首說明解釋了但藥方沒有——**謄錄錯位**
- 同一個藥名在不同首註成不同的東西（同名異物，禁忌完全不同）

**照抄並註明「此為原始典藏之狀態」，不要自作聰明修正。**
你修了，就變成你的版本，而你沒有那個權威。

同樣地，有 12 首的典藏**自帶警語**（原文就寫「藥方請勿使用」）。
我們的措辭是「**此警語出自原始典藏，非本站加註**」——
把別人的判斷說成自己的，跟杜撰是同一類錯。

## 二、把編輯標準做成機器 gate

這是本文第二個核心。**人眼一定會漏**，特別是當你每天在改一個上萬頁的站。

folk.tw 現在有 12 道 gate，build 不過就不部署：

| Gate | 擋什麼 |
|---|---|
| `check:integrity` | 資料參照斷鏈、無源實體 |
| `check:rendered` | **全量**渲染不變量（見下） |
| `check:canonical` | 內部連結的網址形式 |
| `check:outbound-urls` | 主動送給搜尋引擎的網址形式 |
| `check:copy-voice` | 產品文案的 AI 腔 |
| `check:content` | 文章正文的 AI 腔 |
| `check:design` / `check:design-tokens` | 設計系統（顏色、字級） |
| `check:scoped-styles` | 一類靜默失效的 CSS bug |
| `verify:almanac` | 曆法計算與三方比對 |

### 2.1 驗證要全量，不要抽驗

`check:rendered` 每次 build 會做這些事——**逐頁**，不是抽樣：

- 7,891 間廟頁逐一比對：摘要存在、結構化資料存在、分享圖指向本廟且檔案真的存在
- 351 個鄉鎮頁：頁面上寫的間數與資料逐一相符
- 75 位神明頁：聖誕日做「農曆→國曆→農曆」**往返驗證**
- 17 個擇日頁共 158 個「宜」日：**逐日翻到該日的曆法頁**比對是否牴觸禁忌

抽驗會過、全量才抓得到的錯，我們遇過好幾次。其中一次是：
**7 位神明的標題會顯示錯誤的日期**——因為某些神有多個誕辰日，
程式取「標籤」用第一筆、取「日期」用最近一筆，兩者不是同一筆。
人工看十頁都正常，全量 gate 一跑就抓到。

### 2.2 新增 gate 一定要做反例測試

寫完 gate 之後，**故意把錯誤的東西放回去，確認它真的擋得住**。
沒做反例測試的 gate，有一半的機率是永遠不會觸發的裝飾品。

### 2.3 gate 要擋句型，不要擋字面

我們有一道 gate 專門擋「AI 療癒腔」——因為站主反覆要求「文案要像真人講話」，
但人眼每次都會漏。

第一版只擋了被抓到的那一整句。結果同樣的腔調換個接法就繞過去了，
一個月後又出現在同一個頁面上。

**修法是擋句型**：那個腔調的特徵是「替使用者想像一個溫情場景」
（有人在等你、你的回報會照亮誰）。把這個模式寫成規則，變體就一起擋掉。

### 2.4 gate 會有盲區

我們的文案 gate 只掃 `.astro`（UI 檔），文章 gate 只掃 `.md`。
結果**由 AI 產製、存在資料 JSON 裡的散文，兩道都不掃**——
330 首藥籤的醫師解說就是這種，四段 × 330 首完全沒被檢查過。

**定期問一次「我的 gate 掃不到哪裡」**，比再多加一道 gate 有用。

## 三、SEO：什麼有效、什麼是幻覺

### 3.1 長尾會給你曝光，但長尾不會給你成長

我們有 7,891 間廟，每間一頁。這批頁面現在佔全站曝光的 **91%**。
看起來很成功——但同一份數據裡，**全站曝光 ≥100 的「非廟名」查詢只有 1 個**
（5,633 個查詢裡有 4,175 個是廟名）。

意思是：**我們在「有人搜特定廟名」時排得很好，在「有人搜這個主題」時等於不存在。**

長尾的問題是它有天花板。搜「○○宮」的人數是固定的，你把 7,891 頁都做到第一名，
也就是那些人。要成長必須拿到頭部詞，而頭部詞要的是完全不同的東西。

**換成你的傳統**：塔羅站有 78 張牌 × N 種牌陣的長尾，占星站有 12×12 的組合長尾。
那些頁面會給你曝光，但「塔羅牌意思」「今日運勢」這種頭部詞不會自己來。

### 3.2 在地意圖的仗，你打不贏地圖

我們做過一次分層分析，結果很清楚：

> 廟宇頁按排名分層看 CTR：**第 1–10 名只有產業基準的 0.17～0.42 倍**，
> **第 11 名以後是正常的 0.99 倍**。

排在前面反而點擊率低——只有一個解釋：那些字是廟名查詢，
搜尋結果上方被 Google 的地圖包（Google Maps 卡片）吃走了點擊。

後來使用者問「能不能加上附近的店家資訊」（我們有擇日功能，理髮吉日之類），
我們查了資料：OpenStreetMap 全台理髮店 2,039 筆，
**只有 765 筆有地址、239 筆有電話**——涵蓋率約 2.5%。

**結論是不做名錄，改做動線**：頁面上放一個地圖搜尋的深連結，
使用者的裝置定位，我們不存任何店家資料。
使用者拿到我們給得起的（哪天適合），Google 給它擅長的（哪家店）。

**通則：不要拿比對方差的資料，進對方主場打。**

### 3.3 模板化的 meta description 等於沒有

我們曾經有 **7,869 個頁面的 description 一字不差**（結尾都是同一句品牌宣傳）。
那批頁面的 CTR 是 1.76%。

修法是**依序取每頁天然不同的既有資料**：沿革首句 → 主祀神誕辰 → 鄉鎮脈絡 → 是否可求籤。
零新增事實，全部是既有欄位的重組。

換成塔羅：不要每張牌的 description 都是「XX 牌的含義與解讀」，
用該牌獨有的元素（元素、數字、對應星體、正逆位差異）組出不同的句子。

### 3.4 薄列表頁不會被收錄

我們的鄉鎮頁（「某鄉鎮的宮廟」）原本只有「共 N 間」加一串清單。
GSC 抽驗 40 頁，**收錄率 57%，全站最低**（廟宇頁是 88%）。

補的內容全部由既有資料衍生：間數＋主祀神分布＋在全縣的排名與佔比。
關鍵是**每個鄉鎮的統計天然不同**，所以頁面之間不再是同一套模板句。

### 3.5 內部連結：三個具體的坑

1. **網址形式要一致。** 我們的 `/poems/` 樞紐一度**內鏈數＝0、從未被爬**——
   因為 sitemap 收的是帶尾斜線的版本，而全站導覽指的是不帶斜線的版本，
   權重全卡在 301 轉址的來源端。這個問題在同一個站復發過三次，
   最後做成兩道 gate 才根治。
2. **不要建密網。** 廟宇頁之間只做單向、上限 5 條的鄰近連結，不互相全連。
3. **主動送出去的網址也要檢查。** 我們有一支腳本每次部署後通知搜尋引擎，
   裡面 9 個高槓桿網址有 8 個形式錯誤，**每次部署都在送轉址網址給 Google**，
   而站台本身的輸出是乾淨的——這是第一道 gate 的盲區，要第二道才抓得到。

### 3.6 清單排序：依「多久遇到一次」，不是依搜尋量

我們有 11 種擇日頁（結婚、理髮、搬家…）。
最初照建置順序排，站主的指示是**依發生頻率排，越常碰到的越前面**：

> 拜拜 → 理髮 → 出行 → 搬家 → 安床 → 開市 → 結婚 → 訂婚 → 安葬 → 動土 → 上樑

「結婚」的搜尋量是這批裡最高的，但一生只碰一兩次。
使用者打開清單時，要先看到**這個月就會用到的**。

換成塔羅：牌陣列表不要照牌陣的知名度排，照「新手第一次會用哪個」排。

## 四、讓 AI 每天自動改站？可以，但護欄要先蓋好

folk.tw 每天有一個自動流程：抓數據 → 決定要改什麼 → 直接改站台檔 → 跑 gate → 部署。

這件事會成立，是因為護欄先於能力：

1. **可改檔案白名單**（glob）。越界就整批撤回，當天不部署。
2. **每天最多改 N 個檔**，寧少勿多。沒有夠格的訊號就 no-op（完全不動）。
3. **事實型內容要先查權威源**，查不到就只准動內部連結與 meta，不准碰事實。
4. **不做高風險操作**：刪頁、改網址、大改版一律禁止。
5. **防震盪**：同一個決定 7 天內改過就不再反覆（含改回去）。
6. **所有 gate 照跑**，不過就不部署——自動流程沒有豁免權。

**沒有這些護欄之前，不要開自動化。** 一個會自己改站的 AI 加上沒有 gate 的 repo，
壞得比人快得多。

## 五、你會遇到「拿不到資料」，而原因不只一種

### 5.1 地域封鎖：用「笨水管」，不要搬家

台灣的政府宗教資料庫**擋境外 IP**。我們的主機在境外。

解法不是搬主機——因為**只有「取資料」需要在地 IP**，
解析、查證、驗證、部署都可以留在原地。

所以架了一台在地的小主機當**笨水管**：
- 照一份清單抓，送原始 bytes，**一行都不解析**
- 每個檔附 sha256 與 metadata
- 收件端驗雜湊、驗筆數、原子換檔

兩個實際踩到的坑，如果你要做這個模式一定會遇到：
- **同步工具的「跳過相同大小的檔案」選項會害死你**：雜湊側檔是固定長度，
  永遠傳不過去，最後變成新資料配舊雜湊，整份驗不過。
- **「檔案大小下限」擋不住截斷檔**：一個 5 MB 的截斷檔通過了 4 MB 的下限，
  **覆蓋掉完整的 6.27 MB 檔**。要有**相對**檢查（不得比現有檔小 10% 以上）
  與**內容筆數下限**兩道，絕對值下限單獨沒用。

還有一個組織面的教訓：**兩端各有一個 AI，中間只能靠人傳話時，
「把工單寫進 repo」不等於「送達」。** 我在同一天犯了三次同樣的錯——
寫好工單卻沒給對方可以直接執行的指令，工單就躺在那裡沒人動。

### 5.2 授權：政府典藏 ≠ 可自由使用

這一條害我們白跑一輪。

我們在政府典藏平台找到一整批廟方製作的籤詩印版，
「創作者」欄直接寫宮廟名——版本錨定條件完美。

**但每一筆的授權都是「僅限於本平台有限度公開瀏覽」。**
看得到、抓得到、不能轉載。全站一致，零例外。

對照組：另一批藥籤資料是「公眾領域標章（PDM）」＋「政府資料開放授權（OGDL）」，
那批我們就用了，330 首全收。

**判準要在動手之前先看**：授權欄寫什麼決定這筆資料能不能用，
不是「它在政府網站上」決定的。

### 5.3 有些東西存在，只是還沒數位化

我們最後找到一筆：某公立館藏有一本完整的一百首籤詩剪貼本，有登錄號、
版本可追到特定寺廟——**但「是否數位化：否」**，線上只有著錄。

這跟「找不到」是不同的處境。它把問題從「這個資料不存在」
變成「要去跟機構申請閱覽」，而那是一條有明確管道的路。

**查到「沒有數位版」也是有價值的答案**，別把它當成失敗。

---

## 六、技術上值得抄的幾個做法

1. **靜態站 ＋ 前端即時算「會過期的東西」。**
   我們的倒數（「還有 N 天」）在 build 時不算，改由前端依時區即時算。
   這樣就算某天沒有重新部署，倒數也永遠是對的。
   凡是「跟今天有關」的顯示，都用這個模式。

2. **顯示邏輯只能有一個入口。**
   「哪一筆是代表祭典」這種推導只寫在一個檔，頁面、分享圖、gate 三處共用。
   多寫一次就多一個會漂移的地方。

3. **資料驅動導覽，不要硬編。**
   我們曾經硬編導覽選單裡的擇日項目，資料長到 11 個時選單還顯示 3 個。
   改成從資料檔讀，之後新增自動跟上。

4. **匯入腳本預設乾跑**，加參數才寫入；並且要 idempotent（重跑不會重複寫）。

5. **註解要寫「為什麼」與「不要改回去」。**
   我們的程式碼裡有大量這種註解：
   > ⚠️ 別改回 `flex-direction: column`——2026-08-02 實測，7 項直排會吃掉手機第一屏。

   半年後的你（或另一個 AI）會想「這寫得好奇怪，我來優化一下」。

**最容易被低估的一格是最後一行。** 如果你的傳統有可計算的部分（星曆、曆法、數字命理），
那部分是你最容易做出「別人抄不走的正確性」的地方——
因為它可以被驗證，而驗證可以做成 gate。

我們的曆法模組會用三套獨立實作交叉比對 1901–2099 的每一天。
占星的星曆同理：拿 Swiss Ephemeris 之類的權威實作對答案，寫成測試。

**最容易被高估的一格是「內容量」。** 78 張牌寫得再詳細，
如果沒有版本標示、沒有來源，那就是網路上第三百個同樣的東西。

## 八、我們還沒解決的

誠實列出來，免得你以為這條路走得通順：

1. **頭部詞覆蓋率仍然是零。** 43 天、66,315 曝光，但那五個我們最想要的主題詞，
   曝光還是 0。長尾撐起 91%，這件事沒有解。
2. **觀音一百籤收不到。** 三輪偵察的結論是線上沒有版本明確的全文，
   唯一的路是去公立館申請閱覽一本未數位化的藏品。**我們寧可不收也不用二手來源。**
3. **兩套新收的籤共 55 首沒有白話解。** 只有籤版原印的分項判語。
   要補就是原創寫作，那是另一種工作量。
4. **官方資料本身有缺漏。** 我們的廟宇資料來自政府開放資料，
   但已經發現至少一間國定古蹟等級的廟不在裡面。
   **不要假設官方資料是完整的。**
